# 让觅食生态型看得见（wire v10 + 点着色器，2026-08-04）

`docs/multispecies_feasibility.md` §17/§18 判决：草↔果觅食生态型的分裂**是真的**
——4 臂 × 4 个 `Ne` = 16 格全部在 p<0.005 上拒绝中性零假设。
**但屏幕上完全看不见它**：颜色只承载 `diet`，一个已经裂成两个食草生态型的世界
和一个没裂的世界长得一模一样。这一节记录把它画出来的改动与验收。

## 2. 着色的两个非显然决定

**[对应] 中性个体必须保持原色。** 调制写成
`c = mix(c, spec * b, w)` 且 **`w` 在 `pref = 0.5` 处恰为 0**。
于是 `web/render.js` 里那句 `vec3 herb = vec3(0.62, 0.32, 0.92);`
——`scripts/check.py:check_species_colours` 钉住的那个字面量——
**仍然是「一个没有专精的食草者」的颜色**，而不是变成一个谁都不是的颜色。
（措辞要准：亮度、armor、venom 本来就已经把最终像素挪离 `#9e52eb`，
所以约束是**字面量不变**，不是**像素相等**。）

**[本世界实测] 斜坡的定标点 0.22 是量出来的，不是挑的。**
第一版写 `w = min(|f| / 0.5, 1) * 0.8`，结果**果专精染上了琥珀，草专精是一片说不清的
灰白**。原因在数据里：`R38n` 后半程的真实分布是

```
下簇质心 0.151（质量 0.450）   上簇质心 0.720（质量 0.498）
中间 [0.35, 0.60) 几乎全空：0.00 / 0.00 / 0.01 / 0.21 %
```

上簇离中性只有 **0.22**，在 0.5 的斜坡上只拿到 0.35 的权重，**压不过紫色底里 0.92 的蓝**。
改成 `min(|f| / 0.22, 1) * 0.85` 之后草那一侧才出现。
**教训与 `MEMORY.md` 里那三条同型：读数（这里是调色板）必须对着被测对象的真实分布定标，
不能对着值域的中点定标。**

**[对应] 属性槽维持在 8 个。** 这个 program 原本正好 8 个顶点属性，
而 **8 就是 WebGL 1.0 保证的 `MAX_VERTEX_ATTRIBS` 下限**。加 `a_forage` 会变 9——
实机与 swiftshader 都给 16，会过，但那是在赌规格。
把 wire 里相邻的 `diet` 与 `energy` 并成一个 `vec2 a_de`，腾出的槽给 `a_forage`，
总数仍是 8。

**⚠️ [对应] 草绿与中毒绿撞车。** 草专精是 `(0.35, 0.85, 0.45)`，
而 venom 的病绿是 `(0.35, 0.85, 0.30)`——**只差蓝通道 0.15**。
满毒的肉食者渲染成 `(0.53, 0.67, 0.29)`，主色道也是绿。
本文的数字**不受影响**（`R38n` 由构造关掉了捕食通道 ⇒ `venom ≡ 0`；
默认世界实测绿 0.001），但**一个演化出尖刺的默认世界里，画面上的绿点会同时意味着两件事**。
要么把草侧推向青绿，要么在读图时记住这一条。

## 3. 补上的契约：per-agent record 的宽度此前完全没人管

`check_wire_protocol` 查的全是 header。**per-agent 那一段一直是裸的。**
它坏掉的表现是 `protocol.encode` 每个 agent 写 K 个 float 而 `main.js` 按 K−1 读，
于是**从第二个 agent 起每一个字段都错位**——画面照样画出来，颜色/大小/位置全是别人的。

`check_agent_stride` 查四处自洽：

1. `protocol.py` 的 `np.empty((n, K))` == `main.js` 的 `STRIDE = K`；
2. `encode()` 恰好填满 `0..K−1` 每一列——少填一列同样静默
   （那一列会是 `np.empty` 的未初始化内存）；
3. `render.js` 每个 `vertexAttribPointer` 的**末字节** `offset + 4*分量数` ≤ `K*4`；
4. 匹配到的 pointer 条数 == 实际启用的属性数（减 1，`a_h` 走另一个 buffer）。

**第 3 条查的是末字节而不是首字节，这不是讲究**：一个 `vec2` 属性从 offset 36 起会读到
40，而 `36 < 40` 会让只查首字节的版本静默通过、实际越界读到**下一个 agent 的 x**。
v10 把 `diet`+`energy` 并成 `vec2` 这一步，正是第一次让这个洞可被触发——
**改动自己造出了它自己的检查缺口**，这条是审查抓出来的。

**第 4 条是给正则本身兜底**：只靠 `pt.` 锚定时，某条 pointer 若写成别的形式就会
从匹配集里掉出去，最大末字节被低估、第 3 条静默通过。条数交叉核对让这种情况直接失败。

**三条断言都做过反向注入验证**（一个从不失败的检查器是没用的）：
`STRIDE` 改 10 而 protocol 仍写 9 ⇒ 「protocol.py writes 9, main.js reads 10」；
`a_forage` 偏移 36→37 ⇒ 「an attribute ends at 41, past 10 floats」；
把一条 pointer 的 offset 写成 `16 + 16` ⇒ 「7 attributes enabled ... but 6 pointer calls matched」。

## 4. `--speed`：headless 验证没有手

`scripts/run_live.py --speed N` 通过环境变量设 `Sim.speed` 的初值，与 `--set` 同路。
装它的理由是 §5 的验收：dashboard 的滑块只能用鼠标拖，而默认 4 步/帧下
`R38n` 需要**几分钟**墙钟时间才演化出可看的东西。
`docs/conventions.md` §10 要的是**用眼睛看**，不是要人有耐心。

**它最初不同步到 UI，那是个真 footgun，已在 wire v11 修掉**：

`web/main.js` 曾硬写 `let speed = 4`，而 header 里没有 speed 字段，客户端只在拖滑块时才发。
于是 `--speed 2000` 时面板显示「FLA 加速率 **4** 步/帧」，
且「窗口长度」（`frames × speed`）**少算 500 倍**。
**一个报出自己编造的步率的 dashboard，比一个不报的更糟。**

**wire v11**：header 追加最后一个 f32 `speed`（offset 72，header 72→76）。
追加到 header 会移动 agent 块，所以 `HEADER_BYTES` 是客户端唯一需要改的常量，
**每一个既有 header 偏移都没动**。截图实测：面板现在显示
**「FLA 加速率 2000 步/帧」**、**「窗口 2,000 步」**。

**⚠️ 剩下的那一半没修，也修不了**：滑块能发的上限是 **256**
（`SPEEDS = [1,2,4,…,256]`），而服务端钳位是 1..2000。
**服务器比 256 快时碰一下滑块，速度就永久掉下去、UI 上回不去。**
现在至少屏幕上的数不是编的了。

> **[更正] `cc3045a` 的提交信息里写着「范围钳在 1..2000，与 dashboard 滑块能发的范围一致」
> ——那句是错的。** 1..2000 匹配的是服务端的钳位，滑块只到 256。
> 提交已推送不便改写历史，更正记在这里。

## 5. 验收（`docs/conventions.md` §10）

截图用 headless chrome + swiftshader
（`--use-gl=angle --use-angle=swiftshader --enable-unsafe-swiftshader`，1600×1000）。

⚠️ 端口用 **8137**，不是默认的 8000——那台机器上 8000 被别的服务占着。

> **⚠️ [更正] 本节初版的闸一与闸二对照组，都是用**定标前**的着色器拍的。**
> 我先拍图、后重定标斜坡（§2），于是出厂的着色器一度**没有闸一证据**，
> 而闸二等于拿两个不同的着色器在比。下表全部已用**出厂着色器**重拍。
> 初版还把「权重上限」写成 **0.24**——那是用**被废弃的公式** `0.15/0.5×0.8` 算的。
> 一篇通篇强调「判据可复算」的文档里，唯一一个读者能独立复算的推导偏了 2.4 倍，
> **错着比没有更糟**。

**闸一：正确性（不依赖演化）。** 默认世界，改动前后各一张，**均为出厂着色器**。

- 变化像素 **13859（0.866%）**，**右侧 UI 面板内变化 0** ⇒ 改动只碰了 agent 着色
  （面板恰为 x ∈ [1280,1600)，画布止于 1262，所以这条断言的划分是精确的；
  对一个「计数为 0」的断言，多包含画布只会让它更难通过，不会更容易）；
- 变化像素的平均 RGB 从 `(89,49,132)` 到 `(89,67,109)`；
- 「绿>红」**0.000 → 0.191**、「红>蓝」**0.006 → 0.194**。

**[本世界实测] 这一闸的可证伪之处在「对称」，不在「小」。**
出厂斜坡下权重上限是 **0.58**（`pref=0.65`，即 `min(0.15/0.22,1)×0.85`），
1σ 处（`sigmoid(±0.4) = 0.401/0.599`）是 **0.38**——**染色一点都不小**。
真正该预期的是：中性种群的 `pref` 关于 0.5 **对称**，所以琥珀与绿**各占一半、
在均值上互相抵消**，于是平均 RGB 只小幅位移，而两个方向的翻转比例几乎相等
（0.191 vs 0.194）。**偏移写错时 `v_forage` 会读到 `venom` 或记录外的内存，
那既不对称也不会保持这个比例。**

**闸二：现象（依赖演化）。** `R38n` 覆盖 + `--speed 2000`，跑 300 秒墙钟后截图。
按主色道给世界画布内足够亮且饱和的像素分类（**两行同一个出厂着色器**）：

| 截图 | 琥珀（果） | 绿（草） | 紫（中性） |
| --- | --- | --- | --- |
| 默认世界（`forage_tradeoff=0`，中性） | 0.056 | **0.001** | 0.943 |
| **`R38n`** | **0.257** | **0.060** | **0.684** |

⇒ 琥珀 **4.6×**、绿 **60×**。
（默认世界那 5.6% 的「琥珀」里含**肉食者**——肉食红本来就 R>B。）

**[本世界实测] 果专精成团、草专精弥散。** 这句话最初是**看图看出来的**，
全篇唯一一条没有数字支撑的断言——所以补量了。
离散指数（25px 格内计数的方差÷均值；完全随机时 ≈1）：

| 截图 / 类 | VMR | 打乱位置的零分布 | 相对随机 |
| --- | --- | --- | --- |
| `R38n` 琥珀（果专精，n=6416） | **88.43** | 1.13 ± 0.04 | **78×** |
| `R38n` 绿（草专精，n=1492） | 8.87 | 1.03 ± 0.03 | 8.6× |
| **默认世界 琥珀（对照，n=2711）** | 18.72 | 1.06 ± 0.03 | **17.7×** |

**打乱零分布保留了每个精灵的像素 footprint**（它只打散位置、不改点数），
所以上面这些「相对随机」的倍数**已经是校正过的数**——零分布 1.13 vs 1.03
正好量出了琥珀精灵略大一点。**结论因此比「只信比值」更强。**

两个读法，第二个是审查补上的对照：

- `R38n` 内部：果专精比草专精团 **9.97 倍**；
- 跨世界：**agent 本来就聚在水边**（中性世界的琥珀类也有 17.7×），
  而 `R38n` 的果专精是 78×——**在那个基线之上再高 4.4 倍**。

⚠️ 这是**一张截图上的一次测量**，不是多种子实验——只当描述，不当判决。

## 8. 觅食生态型直方图面板（第二个 commit）

着色让分裂在**世界里**可见；面板让它在**数上**可见。**零额外 wire 成本**——
`forage_pref` 已经在 per-agent record 里，20 箱直方图与 `low_mass` 都由客户端现算。

**三条约束写死在代码里**：

1. **只统计食草者**（`diet < 0.35`，offset 2）。`trajectory.py:_hist_fn` 是
   `alive & (diet < 0.35)`，而默认世界里肉食者占五分之一——不过滤就等于画了另一个量。
2. **分箱必须与分析脚本一致**：20 箱、覆盖完整 [0,1]、**端点 clip 而非丢弃**。
   `main.js` 里那个常量带 `CONTRACT:` 注释，并由 `scripts/check.py:check_ecotype_bins`
   钉到 `trajectory.py` 的 `BINS = np.linspace(0.0, 1.0, 21)` 上（做过反向注入验证：
   把 `EC_BINS` 改成 14 会立刻 FAIL 并报「trajectory.py has 20 bins, main.js draws 14」）。
   **分箱公式**（clip 而非丢弃）由 Python 端的
   `tests/test_neutral_null.py::test_hist_of_counts_every_individual` 守；JS 端不测。
3. **不画 `split_score`**（理由见 §6）。柱子的颜色用与着色器**同一条**斜坡，
   所以世界里的一团和面板里的一个峰认得出是同一群。

**这一闸不是「看起来像双峰」**，而是「客户端现算的数是否复现已知值」：

> **[本世界实测]** 面板的 `low_mass` 与分析脚本的 `low_mass` 在两个方向上都吻合

## 9. 2026-08-17 复验：面板确实能实时看到分裂，**但默认世界看不到**

§8 的面板做完之后，一直没人在**真的会分裂的世界**上看过它——验收用的是默认配置，
而默认配置**不产生生态型分化**（那是九项干预累积出来的，`multispecies_feasibility.md`
§10–§18）。所以「面板能显示分裂」此前只是推理，不是观察。

**[本世界实测] 复验通过。** 带上判决那一臂的完整覆盖启动：

```bash
XLA_PYTHON_CLIENT_PREALLOCATE=false .venv/bin/python scripts/run_live.py --speed 50 \
  --set fruit_energy=4.0 --set fruit_water_frac=0.40 --set plant_max=2.0 \
  --set water_sea_dist=1 --set grass_shade=1.3 --set forage_tradeoff=1.0 \
  --set forage_curvature=1.0 --set eat_rate=0.5 --set ridge_wavenumber=1 \
  --set fruit_regrow_baseline=0.25 --set regrow_baseline=0.010 --set diet_delta=1.5
```

约 **150 秒**后（`--speed 50`，种群 5426、平均年龄 847）截图所见：
- 面板读数 **47% 偏果**，直方图**明确两个峰、中间空白**；
- **世界里同时可见**：橙色个体聚成一簇簇扎在结果子的斑块上，绿色散在开阔处
  ——与 `explorations/20260816-replay/map.html` 的「偏果的 77–85% 站在果子地上」
  是同一件事的两种呈现。

对照：**默认配置**跑同一个面板，读数 6% 偏果、单峰。⇒ **面板没问题，是世界的问题。**

⚠️ **因此凡是让人「跑 `run_live.py` 看分化」的说明，都必须带上这十二项覆盖**
（`explorations/20260816-replay/index.html` 初版漏了，已修）。
删掉最后的 `--set diet_delta=1.5` 就把捕食者放回来，几分钟内橙色那一支消失
——这是 §27/§30 判决最省事的现场演示。
